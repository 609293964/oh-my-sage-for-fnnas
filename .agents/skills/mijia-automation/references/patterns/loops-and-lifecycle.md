# 循环与生命周期模式

本文件是跨案例设计指导，不表示其中每个完整拓扑均已实机验证。具体运行结论以案例和实验的证据状态为准。

## 可控循环

```text
开始事件 → loop.start
loop.output → 检查状态/生成参数 → 动作
停止事件或退出条件 → loop.stop
```

每个 loop 必须有：

- 明确启动条件。
- 明确停止条件。
- 每轮仍需满足的状态检查。
- 最大值、最大次数或安全上限。
- 规则禁用、设备关闭和异常路径的停止方式。

已验证的退出拓扑：

```text
start → loop.start
loop.output → 业务动作 + counter.input
counter(n=3).output → loop.stop
取消/恢复/异常事件 → loop.stop
新一轮开始前 → counter.zero
```

只在动作前加 `onlyNTimes` 不会停止 loop 本身；限制动作次数和停止定时器是两件事。

## 保存和恢复设备状态

```text
开始前查询原值 → 临时变量
执行临时动作
结束事件 → 必要的完成提示 → 延时 → 恢复原值
```

恢复值来自设备真实读值，可能低于当前 MIOT 写范围。新写入仍需能力校验；历史恢复值应先确认设备是否接受。

## 状态机而非延时链

跨事件、跨重启或长周期需求优先保存状态和时间戳，不依赖超长 delay/loop。状态变量必须定义所有状态、转换和异常恢复，不能只有单向置位。

内部模式游标与设备状态是两套状态。设备还会被 App、语音、实体开关或其他规则修改时，优先查询设备最近已知状态，再决定下一动作；不要假设模式卡自动归位。

- 纯轮转模式：接受内部游标；空输出也占一个轮次，当前网关已实测。
- 状态驱动模式：每次先查询设备状态，用互斥且完整的区间选择下一动作，不依赖 modeSwitch 游标。

通过补发中间动作让游标归位会真实经过中间模式。加热、门锁、阀门等高风险设备不得使用这种校准方式。

## 启动恢复

启动或来电后执行归位动作时，等待应覆盖网关、网络和目标设备恢复，但固定延时不能证明设备已经可控。增加上线检查、失败重试上限，并防止延迟动作覆盖用户恢复后的手动操作。

## 退出优先

设计循环时先写停止路径，再写循环体。未证明可停止的循环不得部署到正式规则。
