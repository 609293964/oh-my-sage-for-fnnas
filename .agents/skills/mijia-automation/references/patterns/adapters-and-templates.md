# 适配器与模板模式

本文件是跨案例设计指导，不表示其中每个完整拓扑均已实机验证。具体运行结论以案例和实验的证据状态为准。

## 三层结构

```text
输入适配层 → 规范变量契约 → 核心逻辑 → 动作变量契约 → 输出适配层
```

- 输入适配层：把设备属性、事件和私有枚举转换成统一状态。
- 核心逻辑：只依赖变量契约，不绑定具体设备。
- 输出适配层：把动作状态转换为目标设备属性或动作。

适合复杂逻辑、设备经常替换或多规则共享。简单联动不应为了模板化强行增加多层变量。

## 完整归一化

瞬时事件映射为状态时，必须定义置位、复位、超时、重启和离线路径。只有“检测到移动 → 写有人”会永久卡在有人状态。

## 模板复制安全

复制时必须重新处理：

- 新规则 ID。
- 本规则变量 scope 和变量登记。
- global 变量依赖。
- 设备 DID、URN、属性、事件和动作。
- 坐标与未知 cfg 字段。
- 目标家庭的能力差异。

不能只替换显示名称，也不能保留源规则的 `R<graphId>`。

## 观测探针

未知事件参数先用无副作用规则采集：

```text
设备事件参数 → 临时变量 → 日志
```

发现规则不控制设备。候选映射应由独立验证规则和无害反馈重复确认，避免自证循环。

## 虚拟事件协同

当前中枢网关已验证规则可产生并消费字符串虚拟事件：

```text
生产：gateway deviceOutput(siid=4, aiid=1, ins piid=1 string)
消费：gateway deviceInput(siid=4, eiid=1, argument piid=1 string = 同名值)
```

虚拟事件是瞬时脉冲，不是持久状态。名称和字符串参数必须完全匹配。“当任一事件发生”的图内输入端口不是虚拟事件对象。

仍需把以下能力拆开验证：

1. App 是否必须负责创建、命名或通知桥接。
2. MCP 与 App 往返时，名称、作用域和触发次数是否一致。
3. 重复事件、跨规则和网关重启后的行为。

关于第 1 点已有 video 级证据：把语音短语接到虚拟事件上时，是在 App 中新建手动控制、令其动作为“中枢网关产生指定名称的虚拟事件”，再在该控制的更多设置中挂载语音自定义指令；规则侧只消费该事件。这说明入口创建与语音绑定发生在 App 侧，但尚未验证同一入口能否完全由 MCP 建立，也未验证语音触发到事件到达的时延。

虚拟事件也不证明设备状态新鲜；入口、出口和 App 前置必须分别记录证据。

## 统一应答入口与分发

多个提问共用一个回答短语时，用“单入口 + 上下文寄存器”分发，而不是给每个问题各建一个短语：

```text
各提问规则：提问动作 ─┬─> 通知/播报
                      └─> 对应寄存器置位（见 state-and-scope 时间窗寄存器）

App 侧：语音短语/手动入口 → 产生同一个虚拟事件

分发规则：虚拟事件 ─┬─> 查询 寄存器_i == 1 → 执行第 i 项动作
                    └─> 汇总 == 0 → 默认分支（见 aggregation-and-thresholds 求和兜底）
```

设计要点：

- 入口只负责“用户应答了”，语义完全由寄存器承载；入口本身不带参数时更要保证寄存器互斥。
- 同义短语应指向同一入口，而不是复制整套分发逻辑。
- 提问后若需要免唤醒继续对话，唤醒动作要排在播报之后并留足播报时长；该时长依赖具体设备与文案，属于经验值，不能固化进模板。
- 分发规则不应假设提问规则一定成功；寄存器为空时的默认分支是必需路径，不是可选优化。

这是 PAT-STATE-01、PAT-ADAPT-01 与 PAT-AGG-01 的组合用法，不单独占用模式 ID。

门锁、门铃和人员相关数据属于高敏感信息，只保存本机脱敏结论，不进入公开模板。
