# 状态与作用域模式

本文件是跨案例设计指导，不表示其中每个完整拓扑均已实机验证。具体运行结论以案例和实验的证据状态为准。

## 何时使用变量

只有以下需求值得引入变量：

- 事件之间需要记住状态或时间点。
- 多个节点重复使用同一个派生结果。
- 采集时机与消费时机分离。
- 多条规则需要共享稳定的状态契约。
- 设备需要通过适配层与核心逻辑解耦。

一次性、线性、无状态的设备联动优先直接连接，避免为模板化增加无收益节点。

## 本规则变量

适用于单条规则内部的中间值、计数器、时间戳、拼接文本和恢复值。

优点：作用域小，不会误触其他规则；删除规则时应随作用域清理。

检查项：

- 变量必须先登记，节点不会隐式创建。
- 初始值不得被当作真实设备状态。
- 规则启用时需要 preload、onLoad 查询或显式初始化屏障。
- 结束路径必须清理计数器、register、loop 和临时状态。

## 全局变量

适用于明确的生产者/消费者契约，例如“房间是否有人”“当前时间段”“家庭模式”。

设计要求：

- 尽量只有一个生产者，多条规则只消费。
- 定义类型、单位、枚举、未知值和初始化时机。
- 值不变时是否产生 `varChange` 事件必须实测。
- 删除或停用生产者前扫描所有消费者。
- 不把设备私有编码直接暴露为全局契约，先归一化。

## 状态缓存与独立消费

```text
设备持续更新 → 状态变量
独立定时/事件 → 读取缓存 → 业务动作
```

适合实时温度定时播报。必须增加新鲜度或初始化判断，否则可能消费旧值。

## 最近已知状态不是物理实时状态

流程中的设备查询可能返回网关最近可用的属性值。设备刚断电、尚未被判离线或上报延迟时，查询结果可能仍是旧值。

- 安全相关动作不得只依赖一次查询结果。
- 为缓存增加最后更新时间、就绪状态或独立在线检查。
- 未知、离线和过期值进入明确异常分支，不要默认当作满足或不满足。
- 外部 App 操作后立即查询时，考虑状态回传延迟和竞态。

`deviceGet.output2` 是“比较不满足”，不是 unknown。需要区分 unknown 时，额外维护就绪变量、采集时间或在线状态；平台无法提供可靠信号时，停止动作并报告无法确认。

## 条件状态与业务触发分离

持续维护一个状态，不代表状态变化时立即执行动作。`condition.condition` 只提供“如果”，还需要独立事件进入 `condition.trigger`。

如果需求是“条件刚成立就执行”，条件更新本身也必须成为触发事件，不能只维护 register。

两个状态谁后成立都应触发时，使用对称结构：`(A事件且B状态) 或 (B事件且A状态)`，再汇合动作。需要处理近同时到达、重复上报和动作去重。
